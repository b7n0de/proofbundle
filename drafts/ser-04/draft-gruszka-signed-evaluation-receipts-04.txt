                       Signed Evaluation Receipts
              draft-gruszka-signed-evaluation-receipts-04

Abstract

   This document defines a Signed Evaluation Receipt: one JSON object
   that records one evaluation result, whether a stated threshold held
   for a stated metric of a stated test suite, and signs it with Ed25519
   over a domain-separated encoding of its canonical bytes.  A receipt
   shows who signed the recorded bytes.  It does not show that the
   recorded result is true.  A receipt does not prove registration with
   a Transparency Service.  In SCITT, transparency additionally requires
   registering a Signed Statement carrying the receipt or its digest
   with a Transparency Service and verifying the resulting SCITT
   Receipt.  Registration and verification of the resulting SCITT
   Receipt are outside this document.

1.  Introduction

   Evaluation results for software and models are often reported as
   numbers in documents, dashboards or logs.  A reader who receives such
   a number later has no means to tell whether the bytes they see are
   the bytes the reporting party produced.  This document defines a
   small, fixed format that gives that means and nothing more.

   A Signed Evaluation Receipt (receipt) holds exactly one assertion:
   for a named test suite and metric, whether the score met a threshold
   under a stated comparator.  The model and the dataset are named only
   through salted commitments.  The assertion is serialized with the
   JSON Canonicalization Scheme [RFC8785], and the resulting bytes are
   signed with Ed25519 [RFC8032] over a pre-authentication encoding that
   binds a fixed type.

   Two parties that share no infrastructure can use this format: an
   Issuer that ran an evaluation, such as the provider of a model or a
   test laboratory, and a Receiver that decides on the result, such as
   an operator that admits a model into service or an auditor.  The
   Issuer hands over one receipt; the Receiver checks it under a key it
   fixed beforehand, without access to the Issuer's systems, and learns
   which result the Issuer reports for which committed model and
   dataset, under which threshold and comparator.  The receipt object
   exists next to the DSSE-compatible signature because it carries,
   together with B, the fixed type and the payload schema identifier and
   is verified by one procedure (Section 5), so that every Receiver
   reaches the same verdict on the same receipt bytes and verification
   key, provided verification completes.  A DSSE signature check alone
   is not that verdict.

   A receipt establishes integrity and origin: the holder of the signing
   key signed exactly these bytes.  It does not establish truth.
   Section 6 lists what a receipt does not prove, and that list is part
   of the definition.  A receipt carries no inclusion proof and names no
   log.  A receipt does not prove registration with a Transparency
   Service.  In SCITT [RFC9943], transparency additionally requires
   registering a Signed Statement carrying the receipt or its digest



Gruszka                   Expires 29 April 2027                 [Page 3]

Internet-Draft         Signed Evaluation Receipts           October 2026


   with a Transparency Service and verifying the resulting SCITT
   Receipt.  Registration and verification of the resulting SCITT
   Receipt are outside this document.

   This document defines an application payload and a receipt that
   carries it with a signature.  Its interoperability target is that
   independent Receivers reach the same format, consistency and
   signature verdict on the same receipt bytes and verification key,
   provided verification completes.  It does not define an evaluation
   method or decide whether a reported result is sufficient for an
   application.  A separate profile can specify how this format is
   carried or cited in SCITT.  This document defines no envelope mapping
   and no transport.

2.  Conventions and Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",

   "OPTIONAL" in this document are to be interpreted as described in BCP
   14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   Issuer:  The party that creates and signs a receipt.

   Receiver:  The party that verifies a receipt.  The Receiver fixes the
      verification key before verification, by means outside this
      document.

   Payload:  The JSON object that holds the assertion (Section 3.2).

   B:  The RFC 8785 byte string of the Payload.  B is what is signed
      (through PAE).

   PAE:  The pre-authentication encoding of Section 4.1.

   Commitment:  A string that binds an identifier without revealing it
      (Section 3.3).

3.  Receipt Format

3.1.  The Receipt Object

   A receipt is one JSON text [RFC8259] that is an I-JSON message
   [RFC7493]: UTF-8 without a byte order mark, no string (member names
   included) that contains a surrogate or noncharacter code point
   ([RFC7493] Section 2.1), no duplicate member names at any level, and
   nothing before or after the JSON text other than insignificant
   whitespace ([RFC8259] Section 2).  Member names are compared after



Gruszka                   Expires 29 April 2027                 [Page 4]

Internet-Draft         Signed Evaluation Receipts           October 2026


   unescaping ([RFC8259] Section 8.3), and so are string values: the
   receipt object is not canonicalized, so \/ and / are the same
   character.  Its top-level value is an object with exactly these
   members:

   schema:  The type of Section 4.2, as a string.

   payload_b64:  The base64 encoding of B ([RFC4648] Section 4, with
      padding).  It MUST be the canonical encoding: re-encoding the
      decoded bytes yields the same string ([RFC4648] Section 3.5).

   signature:  An object with exactly the members alg and sig, or
      exactly alg, sig and key. alg is the string ed25519; sig is the
      canonical base64 encoding, as for payload_b64, of the 64-byte
      Ed25519 signature; key, when present, is the canonical base64
      encoding, as for payload_b64, of a 32-byte Ed25519 public key and
      is only a hint (Section 5).

   The receipt object has no number member.  The number rules of I-JSON
   are not checked when the receipt is parsed: a number where a string
   belongs fails the step that checks that member.

   The receipt names no trust instance: it carries no certificate, no
   address from which a key could be fetched, and no list of trusted
   parties.

   In this document a digit is one of the ASCII digits 0 to 9 (0x30 to

   https://signed-evidence.org/eval-receipt/

   and comes with its own test vectors.  The identifier above keeps
   naming the format of this document.

3.3.  Salted Commitments

   sha256-salted-v1 is defined as follows.  The Issuer takes a salt of
   exactly 16 bytes from a cryptographically secure random source and
   keeps it.  The commitment is the string sha256: followed by the 64
   lowercase hexadecimal digits of SHA-256 over the salt bytes
   immediately followed by the UTF-8 bytes of the identifier.  There is
   no separator and no length prefix.  SHA-256 is the hash function
   specified in [RFC6234].  A Receiver checks only the pattern sha256:
   followed by 64 lowercase hexadecimal digits; it can check the binding
   only when the Issuer discloses salt and identifier.  Reusing the same



Gruszka                   Expires 29 April 2027                 [Page 7]

Internet-Draft         Signed Evaluation Receipts           October 2026


   salt and identifier produces the same commitment across receipts.
   Fresh salts avoid this equality link but do not make receipts
   unlinkable, because verification keys and other shared values may
   still link them (Section 9).

3.4.  The Bytes B

   B is the serialization of the Payload under [RFC8785].  For a valid
   Payload that means: members sorted by name, no insignificant
   whitespace, the integer n as its decimal digits, and strings with the
   escaping of [RFC8785] Section 3.2.2.2.  A Receiver MUST reject
   payload bytes that are not their own RFC 8785 serialization, so that
   exactly one B exists for each Payload.  The check (step 5 of
   Section 5) runs before the member checks of step 6, so it applies RFC
   8785 in full, including the number serialization of its
   Section 3.2.2.3: a B that carries 1.0, 1e0 or 9007199254740993 is not
   its own serialization.

3.5.  The Criteria Digest

   criteria_digest is OPTIONAL.  When present, it is the string sha256:
   followed by the 64 lowercase hexadecimal digits of SHA-256 over the
   bytes of a criteria set, exactly as the publisher of that criteria
   set fixed them.  A criteria set is any document that states how an
   evaluation is to be judged, for example its metric, comparator and
   threshold; this document defines no format and no canonical form for
   it.  A Receiver checks only the pattern (step 7 of Section 5).  It
   can check the binding only when it holds the bytes of the criteria
   set, by computing SHA-256 over them.  What the member does not show
   is part of Section 6.

   As an informative example, the profile of
   [I-D.ozturk-scitt-prml-profile] carries in its hash-only mode the 32
   octets of SHA-256 over the canonical bytes of a criteria set written
   in [PRML] as the payload of a Signed Statement.  When the bytes of
   the criteria set are those canonical bytes, the 64 hexadecimal digits
   of criteria_digest are those 32 octets written in lowercase
   hexadecimal.

4.  Signature

4.1.  Pre-Authentication Encoding

   PAE(type, body) = "DSSEv1" SP LEN(type) SP type SP LEN(body) SP body







Gruszka                   Expires 29 April 2027                 [Page 8]

Internet-Draft         Signed Evaluation Receipts           October 2026


   SP is the byte 0x20.  LEN(x) is the number of bytes of x as ASCII
   decimal digits without leading zeros. type is the UTF-8 string of
   Section 4.2, body is B.  "DSSEv1" is the six ASCII bytes of that
   literal.  This is the pre-authentication encoding of DSSE [DSSE]; it
   is defined here so that this document can be implemented without it.

4.2.  The Type

   The type is the fixed string

   application/vnd.signed-evidence.eval-receipt+json

   It enters every signature.  It MUST NOT change for this format,
   because a change would invalidate every signature made under it; a
   new format uses a new type.  The string is a media type name in the
   vendor tree ([RFC6838] Section 3.2) with the +json structured syntax
   suffix ([RFC6839] Section 3.1).  It is the same string that a DSSE
   envelope would carry as payloadType.

4.3.  Signing

   The signature is Ed25519 as defined in [RFC8032] Section 5.1, in its
   pure form, without context and without prehashing (not Ed25519ctx,
   not Ed25519ph):

   sig = Ed25519-Sign(secret key, PAE(type, B))

4.4.  Verification Profile

   Ed25519 implementations differ on inputs that RFC 8032 leaves to
   choice [TAMING].  A Receiver MUST use this profile.  In it, x*P is
   the scalar multiplication of the point P by the integer x, B' is the
   base point, and L is the order of B' ([RFC8032] Section 5.1).

   1.  The public key A and the signature's first half R MUST be
       canonical encodings: decoding as in [RFC8032] Section 5.1.3
       succeeds.  That decoding rejects a y-coordinate that is not below
       p and the encoding of x = 0 with the sign bit set.

   2.  A and R MUST have order L: L*A and L*R are the neutral element,
       and A and R are not the neutral element.

   3.  The scalar S, the second half of the signature read as a little-
       endian integer, MUST be below L ([RFC8032] Section 5.1.7).







Gruszka                   Expires 29 April 2027                 [Page 9]

Internet-Draft         Signed Evaluation Receipts           October 2026


   4.  With k = SHA-512(R || A || PAE(type, B)) read as a little-endian
       integer reduced modulo L, the equation S*B' = R + k*A MUST hold
       (the cofactorless equation).  In the hash input, R and A are the
       32-byte encodings exactly as received: the first 32 bytes of the
       64-byte signature and the verification key.

   A signature that fails any rule is invalid.  The rules are checked in
   the order given, and within rules 1 and 2 the key before R.  Because
   A and R have order L, the cofactorless equation of rule 4 and the
   cofactored equation 8*S*B' = 8*R + 8*k*A of [RFC8032] Section 5.1.7
   accept exactly the same signatures.  This specification defines
   individual verification only.  A randomized batch result MUST NOT
   substitute for checking all four rules for each signature.  A
   Receiver MUST NOT leave out any of the four rules.

5.  Verification Procedure

   Input: the receipt bytes and the verification key that the Receiver
   fixed.  The verification-key input is exactly 32 octets containing
   the compressed Edwards-point encoding of A defined by [RFC8032]
   Section 5.1.2.  A verification-key input that is not exactly 32
   octets is an input error: the steps below are not run, and the result
   is neither PASS nor the FAIL of one of them.  Any textual or file
   representation used to supply those octets is outside this
   specification.  The steps are evaluated in order; the result is PASS
   only when every step succeeds, and the first step that fails gives
   FAIL.  String values are compared after unescaping.  A Receiver that
   stops because it reached a resource limit (Section 8) reports a
   resource-limit error; that is neither PASS nor the FAIL of one of the
   steps below.

   1.   Parse the receipt as one I-JSON text (Section 3.1).  A byte
        order mark, bytes that are not UTF-8, a surrogate or
        noncharacter code point, duplicate member names at any level,
        anything before or after the JSON text other than insignificant
        whitespace ([RFC8259] Section 2), a top-level value that is not
        an object with exactly the members schema, payload_b64 and
        signature, or a signature that is not an object with exactly alg
        and sig or exactly alg, sig and key: FAIL.

   2.   schema is not the type of Section 4.2: FAIL.

   3.   payload_b64 is not a string of the base64 alphabet with padding,
        or not the canonical encoding of the bytes it decodes to: FAIL.
        Otherwise those bytes are B.






Gruszka                   Expires 29 April 2027                [Page 10]

Internet-Draft         Signed Evaluation Receipts           October 2026


   4.   B is not one I-JSON text whose value is an object, under the
        rules of step 1 (byte order mark, UTF-8, surrogates and
        noncharacters, duplicate names as in [RFC7493] Section 2.3,
        which [RFC8785] Section 3.1 requires of its input, trailing
        data): FAIL.  Numbers are not judged here: each is read as an
        IEEE 754 double, rounded to nearest with ties to even and
        overflowing to infinity, and a number that so has no finite
        double, such as 1e400, fails step 5.

   5.   B is not the RFC 8785 serialization of the value parsed in step
        4 (Section 3.4): FAIL.  This step alone would also reject every
        B that step 4 rejects for a byte order mark, duplicate names or
        trailing data; step 4 is kept so that every Receiver reports the
        same failing step.

   6.   The Payload's member set differs from Section 3.2 (every member
        of Table 1, with criteria_digest optional), or a member violates
        its row of Table 1 (its type, the schema and commit_alg values,
        a non-empty string, the comparator set, the decimal grammar, the
        range of n, the timestamp form): FAIL.

   7.   A commitment, or criteria_digest when present, is not sha256:
        followed by 64 lowercase hexadecimal digits: FAIL.

   8.   passed differs from the comparison of score with threshold:
        FAIL.

   9.   signature.alg is not the string ed25519, or signature.sig is not
        a string that is the canonical base64 encoding of exactly 64
        bytes: FAIL.

   10.  signature.key is present and is not a string that is the
        canonical base64 encoding of the verification key: FAIL.  A key
        in the receipt is only a hint.

   11.  The signature is invalid under the profile of Section 4.4 for
        the verification key and PAE(type, B) with the fixed type: FAIL.
        A signature made over PAE with another type fails here.

   Table 2 lists every vector of the vector set (Appendix A) with the
   step at which it fails first; each of the eleven steps is the first
   failing step of at least one vector.  A vector shows the first
   failing step under in-order evaluation; it does not show that a later

6.  What a Receipt Does Not Prove

   Verification establishes that the receipt passes the format,
   consistency and signature checks in Section 5 under the Receiver's
   selected key.  PASS does not mean that passed is true or that the
   result meets the Receiver's requirements for its intended use.
   Establishing who controls that key and whether that party is
   authorized to make the claim is outside this procedure.  Verification
   does not establish that the Issuer's claims are true.  In particular:

   *  The score can be false.  The evaluation can be wrong, badly
      designed or not run at all; the receipt records what the Issuer
      states.

   *  The run need not have been the only run.  An Issuer can evaluate
      many times and record only the run it prefers.

   *  The Issuer can lie.  A valid signature binds the statement to the
      key, not to the truth.

   *  A receipt does not show that it was published, logged or shown to
      anyone else.  A receipt does not prove registration with a
      Transparency Service.  In SCITT, transparency additionally
      requires registering a Signed Statement carrying the receipt or
      its digest with a Transparency Service and verifying the resulting
      SCITT Receipt.  Registration and verification of the resulting
      SCITT Receipt are outside this document.

   *  The receipt bytes are not a stable name for the receipt.  Only B
      is signed; the receipt object around it is not canonicalized, and
      its key hint can be present or absent.  A party that cites a
      receipt cites SHA-256 over B.

   *  A commitment is computationally binding under the collision
      resistance of SHA-256.  A Receiver can check a claimed opening
      only after receiving the salt and identifier.  Hiding depends on
      keeping an unpredictable salt secret.

   *  The timestamp is the Issuer's statement, not a time attested by
      another party.

   *  The receipt says nothing about individual samples: n is the
      Issuer's statement, and no sample result is committed or can be
      disclosed against the receipt.  A sample-level audit is outside
      this document and is left to a separate document.

   *  A receipt does not show that the threshold was fixed before the
      run.



Gruszka                   Expires 29 April 2027                [Page 16]

Internet-Draft         Signed Evaluation Receipts           October 2026


   *  criteria_digest binds only the Issuer's statement that this result
      belongs to the criteria set with that digest.  It shows neither
      that the criteria set existed before the run nor that the metric,
      comparator and threshold in it equal those in the receipt.

   *  Even with salt and identifier disclosed, the receipt does not show
      that the named model or dataset was the one actually evaluated.

   *  A receipt does not show where B came from.  B carries no reference
      to another receipt or record that it was made from, for example
      when an Issuer translates the result of another format into a
      receipt; this format has no member for it.

7.  Related Work

   The following individual drafts also define signed receipts; each
   sentence states a difference in construction as read on 2026-10-25.

   *  [I-D.farley-acta-signed-receipts] records access control
      decisions, serializes them with RFC 8785, makes Ed25519 mandatory
      to implement, permits ES256 and recommends ML-DSA-65, and offers
      an optional commitment mode that places salted field values in a
      Merkle tree hashed as in Certificate Transparency ([RFC9162]
      Section 2.1.1).

   *  [I-D.chueayen-attestation-receipts] defines two records signed
      with Ed25519: an attestation receipt for an AI inference decision,
      with twelve required members, the signature among them, three
      optional members and no other member; and an action record for the
      decision an enforcement point takes before a proposed agent action
      runs, with thirteen required members and no other member, all
      strings or arrays of strings.  Both use a canonicalization that,
      by its own statement, differs from RFC 8785 only in forbidding
      numbers that RFC 8785 writes in exponential notation.

   *  [I-D.marques-asqav-compliance-receipts] profiles action receipts
      with RFC 8785, requires ML-DSA-65 for new issuance, accepts
      Ed25519 only under a separately selected historical format, and
      requires a hash chain between receipts.

   None of the three, as read on that date, has a member for an
   evaluation threshold.  Two further individual drafts concern
   evaluation evidence without defining a signed result:

   *  [I-D.abak-ai-evaluation-claim-preservation] states format-neutral
      requirements for converting and consuming evaluation evidence so
      that claim-relevant loss stays visible; it defines no wire format,
      while this document defines one signed format for one result.

8.  Security Considerations

   This section follows the guidance of [RFC3552].  The attacker
   considered can read, create, modify, replay and reorder receipts, and
   controls every input except the Receiver's choice of verification
   key.

   Forgery.  Without the secret key an attacker cannot produce a receipt
   that verifies under the Receiver's key, given the security of
   Ed25519.  The Receiver fixes the key out of band; a key carried in
   the receipt is only compared with it and never used on its own.  A
   Receiver that took the key from the receipt would accept any receipt
   from anyone.










Gruszka                   Expires 29 April 2027                [Page 19]

Internet-Draft         Signed Evaluation Receipts           October 2026


   Domain separation.  The signature covers PAE(type, B), not B alone.
   A signature made by the same key for another purpose over the same
   bytes, or over the same bytes under another type, does not verify as
   a receipt, and a receipt signature does not verify as a signature
   over B in another protocol that also signs with PAE under a different
   type.  The type is fixed (Section 4.2) so that this separation does
   not depend on a value the attacker controls.

   Ambiguous bytes.  Duplicate member names (also when they differ only
   in escapes), trailing data, a byte order mark, surrogate or
   noncharacter code points, non-canonical base64 and payload bytes that
   are not their own RFC 8785 form, for example a number written as
   1800.0, would let two parsers see different content behind one
   signature.  The procedure of Section 5 rejects each of them, so that
   one B has one meaning.  The receipt object around B is not canonical
   and not signed (Section 6).

   Ed25519 edge cases.  Implementations of Ed25519 differ in whether
   they accept a non-reduced S, non-canonical point encodings, points of
   small or mixed order, and whether they use the cofactored or the
   cofactorless equation [TAMING].  A receipt format whose verdict
   depends on the library would let one Receiver accept what another
   rejects.  The profile of Section 4.4 fixes each choice.  Vector N12
   shows why rule 2 refuses points of small order: with the neutral
   element as verification key, R = S*B' satisfies the cofactorless
   equation for every message.  N61 and N59 show why rule 2 requires
   order L: under a key or with an R of mixed order the cofactored and
   the cofactorless equation can disagree (N59), and a verifier that
   does not check the order accepts N61 under either equation.  In the
   measurements of Section 11, the plain Ed25519 verification of a
   general library accepted the signatures of vectors N12, N16, N18 and
   N61 and rejected those of N6, N17 and N59; the profile of Section 4.4
   rejects all seven.  A Receiver that relies on a library verdict alone
   therefore does not implement this format.

   Resource limits.  This document defines no universal input-size
   limit.  Oversized inputs, long strings and deeply nested invalid JSON
   can exhaust memory or processing time before verification completes.
   Implementations SHOULD apply documented resource limits before and
   during processing of untrusted input.  Reaching a limit MUST NOT
   produce PASS and is reported as a resource-limit error, not as a
   completed format or signature verdict under Section 5.

   Commitments.  A commitment with a short or guessable salt can be
   tested against candidate identifiers.  The salt is therefore 16 bytes
   from a cryptographically secure source and stays with the Issuer.





Gruszka                   Expires 29 April 2027                [Page 20]

Internet-Draft         Signed Evaluation Receipts           October 2026


   Criteria digest. criteria_digest binds the bytes of a criteria set,
   not a time.  Whoever wants to show that the criteria set existed
   before the run needs an anchor outside the receipt, for example the
   digest of the criteria set registered with a Transparency Service
   before the run began.  The member also carries weight only when the
   Receiver compares it with bytes of the criteria set that it obtained
   independently of the state it checks: criteria bytes taken from the
   same place as the result can have been changed together with it, and
   their digest then matches.

   Replay.  A receipt is a static statement, not an authentication
   token.  Showing a valid receipt proves nothing about the party that
   shows it.

   Key compromise.  A compromised key can sign receipts with any
   content.  This document defines no revocation; a Receiver that needs
   it uses means outside this document.

9.  Privacy Considerations

   Model and dataset identifiers appear only as salted commitments.
   Reusing the same salt and identifier produces the same commitment
   across receipts.  Fresh salts avoid this equality link but do not
   make receipts unlinkable, because verification keys and other shared
   values may still link them: identical suite, metric and timestamp
   values link receipts, and so does the same criteria_digest.
   Disclosing salt and identifier to one Receiver discloses them to
   everyone that Receiver passes them on to.

11.  Implementation Status

   This section records the status of known implementations at the time
   of writing, following [RFC7942], and is to be removed before
   publication.

   The vectors of Appendix A were produced by a generator script whose
   two runs are byte-identical, and verified by two verifiers: one
   written by the author of the generator, and one written from the text
   of this document alone, without access to the generator.  Both
   verifiers reach the expected verdict and the expected first failing
   step on every vector.  An implementation of this format in the
   proofbundle project, behind an explicit option and with these vectors
   as conformance tests, is under way on a work branch and not released.
   The show-eval command of that implementation with --expect-issuer
   refuses a verification key whose y-coordinate is not below p or that

   of a point of mixed order, and S = r + k*a mod L with the issuer's
   secret scalar a.  The cofactored equation 8*S*B' = 8*R + 8*k*A holds

   A verifier uses the file only after its size and SHA-256 are those
   above.  The file is one JSON text [RFC8259] in UTF-8: an object with

   Table 2.  Each object has the members id, label, expected and step,
