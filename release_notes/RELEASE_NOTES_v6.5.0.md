**A feature release following 6.4.0, with an offline Sigstore bundle verifier and stricter in-toto statement checks.** It adds `proofbundle verify-sigstore`, which verifies GitHub Artifact Attestations and npm provenance offline against the trusted root, the artifact digest and the identity the relying party supplies. The verifiers for eval-result v0.1, test-result v0.1 and SVR v0.1 statements now refuse statements that lack the members their predicates require or that carry them in another form, and every `rfc3339z` time field must name a real calendar instant. Statements that a released version accepted with such members missing or malformed no longer verify. That includes statements that earlier exporters of this package emitted from caller-supplied time, claim timestamp or test-result `url` values in another form; the CHANGELOG names each case.

```
python -m pip install --upgrade proofbundle==6.5.0
```

## Highlights

- **`proofbundle verify-sigstore` verifies GitHub Artifact Attestations and npm provenance offline.** It checks one Sigstore bundle under the profiles `github-artifact-attestation`, `npm-provenance` and `npm-publish`, from the Fulcio leaf and its embedded SCT to the inclusion proof and the checkpoint, and an in-toto Statement with a SLSA Provenance v1 predicate. It imports no Sigstore client. `safeForAutomation` is false in every verdict, since revocation and log consistency over time are not checked.
- **Stricter checks for eval-result v0.1, test-result v0.1 and SVR v0.1 statements.** An eval-result v0.1 statement must carry its eight required members, at least one claim, and the required forms of `verifier`, `suite` and `subjectProfile`. A test-result v0.1 statement must carry `result` and `configuration` with the required types. An SVR v0.1 statement must carry `verifier`, `verifier.id`, `timeCreated` and `properties`. The affected URI and timestamp fields are now validated as described in the entries below. `proofbundle intoto --verify` and `proofbundle svr --verify` report the verifier's failure reasons; the meanings of their exit codes are unchanged.
- **Time fields name a real instant.** Every `rfc3339z` time field checks month, day in month, hour, minute and second after its form, so `decision verify --strict` refuses a `decidedAt` of `2026-13-15T09:05:00Z`. The Rust verifier applies the same rule to the one time field it checks.
- **Stricter input and binding checks, and lower memory use in five JSON traversals.** The Bitcoin header map in the trust policy, `--bitcoin-header`, `--bundled-header`, the agent-review policy file and the SD-JWT bundle-binding check now reject inputs or bindings they previously accepted. Five JSON traversals carry paths as links and render path text only when needed for a message, keeping memory use proportional to the input and any supplied path declarations.

## What a receipt still does not prove

A valid signature binds the signed content to the signing key. It does not make a reported result true.

`decision verify` and `outcome verify` do not implement the complete offline verification procedure in draft-gruszka-audit-decision-receipts-05. They do not perform all the procedure's checks for approval records, action bytes, executor identity, separation of keys and identifiers, effects and the execution-time window. `decision verify` also exits 0 when the evaluation time is before `decidedAt`, although Section 3.2 step 9 of revision 05 requires `decidedAt <= T`.

A Statement with two subject entries, which Section 3.2 step 6 does not allow, exits 0 without `--require-derived-subject` and 2 with that switch. Both measurements use `--strict`, the gate-1 public key, `--aud observer-1`, `--nonce dec-0002` and `--verification-time 2026-10-15T09:06:00Z`. The valid V2 control still exits 0 with the switch. These command results are not verdicts of full conformance to revision 05.

Without `--policy`, `decision verify` does not establish that `decisionMaker.id` is the identity trusted for the signing key. In vector F3 of Appendix A.5 of draft-gruszka-audit-decision-receipts-05, the receipt names gate-2 under the gate-1 key. With `--strict`, `--aud observer-1`, `--nonce dec-0002` and `--verification-time 2026-10-15T09:06:00Z`, it exits 0 without a policy and reports `POLICY: NOT_EVALUATED`. The same invocation exits 3 when `--policy` supplies a `trusted_decision_makers` mapping from that key to gate-1. These results depend on the stated verification time; they do not mean that an expired receipt passes without a policy. The command does not read or hash the evidence bytes referenced by `evidenceRefs`, with or without that test policy.

### Added

- **`proofbundle verify-sigstore` verifies GitHub Artifact Attestations and npm provenance offline.** `proofbundle.adapters.sigstore_bundle.verify_sigstore_bundle` checks one Sigstore bundle against the trusted root, the artifact digest and the identity the relying party supplies. It reads media types 0.1 to 0.3, a DSSE envelope and Rekor v1 entries of kind `dsse` and `intoto`, under three profiles: `github-artifact-attestation`, `npm-provenance` and `npm-publish`. It verifies the Fulcio leaf, its chain at every verified time and its embedded SCT, the signed entry timestamp, the inclusion proof and the checkpoint, and an in-toto Statement with a SLSA Provenance v1 predicate under the rules of the two GitHub workflow buildTypes, their four allowed events included. For npm-publish, supplying the version document also checks its `dist.signatures` against the registry's keys. For npm-provenance, supplying package.json also checks its package identity and repository. The reader does not open the tarball; the relying party must supply package.json from the artifact whose digest it provides. Whether the predicate agrees with the certificate is reported as a note, because those rules come from the producers' code and not from a specification. It was written from the specifications pinned in `SPEC_PIN` and imports no Sigstore client. Unknown members of the DSSE envelope are refused, a deviation from DSSE that `docs/SIGSTORE_BUNDLE_VERIFIER.md` names. The exit codes follow the TRACE reader: 0 verified, 1 a cryptographic or structural failure, 2 unreadable input or a feature not implemented, 3 an unmet requirement of the relying party. `safeForAutomation` is false in every verdict, since revocation and log consistency over time are not checked. Each vector of `tests/fixtures/sigstore_bundle/` fails at the step it names, and public bundles of the npm registry and of the cli/cli test data verify offline against the vendored public-good root. It is Python only, and its parity register row is PENDING.

### Fixed

- **Every `rfc3339z` time field must name a real instant, not only have its form.** `decision verify --strict` exited 0 on a decision receipt whose `decidedAt` was `2026-13-15T09:05:00Z` or `2026-10-32T09:05:00Z`, although docs/predicates/decision-receipt.md section 5 states time fields are RFC 3339 under its fail-closed rules, and the same value in `validity.expiresAt` already failed closed. `_schema_shapes.RFC3339_Z` now checks month, day in month and year, hour, minute and second (to 60, the leap second of RFC 3339 5.7) after the form, the rule `intoto._is_rfc3339` already applied, and the decision, outcome, relation, run ledger, subject binding, trust pack and verification summary checks read it. agent-review reads the same check instead of a private copy of the form; by maintainer decision this applies to v0.1, v0.2 and v0.3 rather than introducing a new version, as for the ASCII digit fix, and no receipt or vector in the repository holds a time value of the form that is not a real instant. The Rust verifier in tools/pb_verify_rs applies the same rule to the `declaredAt` of a relationship edge, its one time check, so both verifiers give a receipt with such an edge the same verdict and exit code. The JSON Schema patterns stay the form; a validator refuses more than its schema here.
- **A copy of an owner's release with a later answer no longer extends the window of its identity.** The plugin's hook, and the signer service with the same code, ran the window of a release from the answer of the copy it was reading, so for a card not used yet a copy answered later opened a later window. The window of an identity (card, sha256, session) now runs from the earliest answer the gate has read for it, every copy in the folder `freigaben` and the record `freigaben-erste.json` in the plugin data directory included, which the gate never moves later; a record that does not read, or that has to change and cannot be written, releases nothing. A copy the gate never read stays unknown to it, as `plugins/proofbundle/DECISIONS.md` D119 names (`tests/test_plugin_release_window_first_answer_d119.py`). This entry concerns the plugin under `plugins/`, which the package does not carry; it ships with plugin 0.4.0.

- **Five walks over a JSON value keep their memory in proportion to the input and to the declaration they are given.** `trace_record._canonicalizable` and `trace_record._canonicalizable_value`, `_plain_value.plain_json`, `subject_binding.nested_closure_violations` and `subject_binding.nested_type_violations` gave every child a path string that copied the text of all its ancestors, so a deep input with long member names cost memory in proportion to its children times the length of the path above them. A dict subclass takes the same way: the reading at the call (`canonical._ein_stand`) copies it into a plain dict before either walk sees it, so its own `get` is never asked. A message about a short path is the message it was before. The open member walk of a trace record names at most 64 values without an RFC 8785 form and counts the rest in one finding. `tests/test_walk_paths_are_links_until_a_message_needs_them.py` holds all five walks under 50 times the input, compares 800 generated inputs with a recursive reference walk, 400 for the closure walk and 400 for the type walk, checks 400 refusals of `plain_json` against the path where the generator planted the refused value, and `tests/test_a_declared_path_costs_no_text_per_prefix.py` holds the long declaration under 50 times its size and checks the position against the prefix set on 400 generated declarations.

A value the canonicalizer refuses does not bind. The mutation operator WP-C1 targets the new comparison, and four new test files hold the four readers.
- **`--bitcoin-header` and `--bundled-header` read a header as the trust-policy loader does.** Both took a merkle root through `bytes.fromhex`, which accepts ASCII white space between the byte pairs, and `--bitcoin-header` put such a root, white space and all, into the relying party's header map, which a policy file refuses. `--bundled-header` of `anchor upgrade` also asked `str.isdigit()` of a height, which holds for digits of other scripts. Both now read `HEIGHT:MERKLEROOT_HEX` through one function with the loader's two patterns: a height of ASCII digits and a root of 64 hex digits, each after the white space around it is stripped, and anything else is malformed input (exit 2). `tests/test_both_header_options_build_what_the_policy_takes.py` compares both readers with a hand-written oracle on 600 generated specs.
