**A feature release following 6.3.1, with an experimental SCITT reader, a TRACE verifier and a stricter JSON reader.** It adds `proofbundle.scitt_ccf`, an experimental reader for SCITT Transparent Statements with CCF receipts under the narrow profile `scitt-ccf/v1`, and `proofbundle verify-trace` for TRACE v0.2 Trust Records. The strict JSON reader now refuses non-finite numbers, integer literals outside the inclusive range -(2^53 - 1) to 2^53 - 1, and JSON bytes with a UTF-8 byte order mark or encoded as UTF-16 or UTF-32. Review the inputs your code hands a verifier when upgrading.

```
python -m pip install --upgrade proofbundle==6.4.0
```

## Highlights

- **An experimental reader for SCITT Transparent Statements with CCF receipts.** `proofbundle.scitt_ccf` reads statements under the narrow profile `scitt-ccf/v1`, which follows draft -06 of the CCF profile, and needs the `[scitt]` extra. It is reached only by calling it; no verify path of the package reaches it. The Rust cross verifier `pb_verify_rs`, which is not part of the Python package, gives the same results for statement signatures, Transparent Statements and consistency receipts over shared vectors.
- **`proofbundle verify-trace` verifies TRACE v0.2 Trust Records.** It checks a record against keys, a time window and expectations that the relying party supplies, in the compact JWS form and in the embedded Ed25519 form. A pass is evidence for the relying party's policy, and `safeForAutomation` is false in every verdict.
- **The strict JSON reader rejects non-finite numbers and applies explicit integer and encoding limits.** `loads_strict` refuses `NaN`, `Infinity`, `-Infinity` and every number that becomes infinite, integer literals outside the inclusive range -(2^53 - 1) to 2^53 - 1, and JSON bytes with a UTF-8 byte order mark or in UTF-16 or UTF-32, with `BundleFormatError`. With an `sd_jwt_vc` whose issuer signature verifies, a signed JSON payload refused for a duplicate member or one of these limits now demands and fails `sd-jwt-bundle-binding`. A payload that is not JSON at all remains outside the scope of that binding. Review code that hands a verifier such input.
- **The release run compares its files with the signed candidate.** Before any upload, the tag run compares its sdist and wheel with the pair signed in the candidate block of the short soak and of the Rust differential, and stops when the bytes differ. The build tools are selected at fixed versions through `.github/build-constraints.txt`; the constraints name versions, not archive hashes.

## Verify this release yourself

Use the checksums and build provenance to check the downloaded files. To check the signed pre-tag audit receipt, use a clone at the source commit identified by the build attestation. The commands, prerequisites and limits are in [Verifying a published release](https://github.com/b7n0de/proofbundle/blob/b66e3590b2a0e10c21c6bb8403ff7c8996488077/RELEASE.md#verifying-a-published-release-anyone).

## What a receipt still does not prove

A valid signature binds the signed content to the signing key. It does not make a reported result true.

So are a name bound under `nonlocal`, a name an assignment expression binds inside a comprehension, which Python binds in the scope around the comprehension, and the annotations of a function, and `getattr(x, "name")` and `x.__getattribute__("name")` with a literal name stand for `x.name` inside a chain. The value of a binding under `global` or `nonlocal` is read where it stands, so a lazy import (`global _os`, then `import os` and `_os = os` in a function) is resolved, and a chain of such reads is resolved once per link. `getattr(x, "name", default)` stands for `x.name` or the default, and a default the analysis cannot resolve stands beside the names it can as a possible unresolved result; a reader imported through another module of the package stays a reader, in the findings and in the import closure. Reading a namespace, as in `print(vars(x))` or `x.__dict__ is None`, does not by itself invalidate every guard. An object that the analysis cannot rule out as a module is treated as a possible module, a parameter among them whatever else the function assigns to it. An object built by a class of the same module counts as no module only when the class is plain: bound once, with no decorator, no metaclass or other keyword, no `__new__` bound in its body in any form that binds a name, a match capture among them, and no attribute `__new__` set in its module, also by a setattr whose name is built from constants or whose arguments the gate cannot assign, and only `object` or such classes of the module as bases; a name computed from anything else stays out of reach. An exception for the identified write in `src/proofbundle/canonical.py` is recorded by name in `scripts/core_layer_modules.json`, with its reason, its count and the source of its line. That permission does not by itself establish the runtime effects of the write or that `TYPE_CHECKING` is unchanged. The analysis does not follow module attributes selected by computed names, as in `getattr(module, name)`, treats the first parameter of a method as no module, so a method called through its class with a module as that argument is not seen, and does not cover code it does not parse. A passing result is limited to these checks and is not a proof that no other runtime binding or write exists.
